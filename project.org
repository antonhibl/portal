  invisible region" or, with =org-fold-catch-invisible-edits= set to =error=,
  refuses.

  meanwhile comes back that way, so a blocked task's line can be found; a
  live view keeps the choice its user made.

*** Problem and outcome
=portal-tasks= currently identifies a task by its file stem or folder name and sorts by
that name. A dependency written in the body is useful to a reader but cannot drive
readiness or execution order. Renaming or regrouping tasks would also break dependencies
if their identity were their location.

Add optional stable identity and dependency metadata, show what blocks each task, and
present unfinished work in a deterministic execution order. This is the first of two
changes; [[#nested-tasks][nested tasks]] builds on its identity and ordering rules. This
document specifies future behavior, not an already supported format.

*** Metadata and identity decision
Use human-chosen, stable IDs in YAML for machine-readable references. Use relative
Markdown links for prose and attachments. A path is a location and changes when a task
moves; a title is editable and need not be unique. Opaque UUIDs would add authoring
friction without providing a needed capability here.

#+begin_example
---

status: todo
depends_on:
  - extract-c-interface
---

# Implement the C adapter
#+end_example

- =id= is optional for compatibility. When present, it must be a string matching
  =^[a-z0-9]+(?:-[a-z0-9]+)*$=, unique across the configured task root. Authors choose
  it once and retain it through title changes, renames, moves, and conversions between
  standalone and folder documents. IDs are scoped to one root; cross-root dependencies
  are outside scope.
- Separate effective ID, logical location, source path, and display title. Without =id=,
  keep the existing file-stem/folder-name identity. The nested-task follow-up extends
  that fallback to a root-relative logical path. Existing tasks require no migration.
  Add an explicit ID before moving a referenced task; choosing its current fallback ID
  preserves references when that value fits the explicit-ID grammar. Otherwise update
  references when assigning it.
- Explicit IDs and fallback IDs share one namespace. Duplicate effective IDs are
  conflicts, including an explicit ID colliding with another task's fallback. Also
  retain the existing conflict for two task documents occupying the same logical
  location (=name.md= and =name/content.md=), even if they now declare different IDs.
  Report every source; never pick a winner. Check before completion filtering, and make
  all involved detail URLs report the conflict.
- Resolve =task=ID= and image requests through the discovered ID-to-source map, not by
  building a filename from an ID. Existing URLs work for tasks that keep their effective
  ID. Changing an effective ID deliberately changes its URL; do not add aliases,
  redirects, sidecars, a registry, or generated IDs on read.
- =depends_on= is optional and defaults to =[]=. When present it must be a YAML sequence
  of nonempty strings; reject null, a scalar, and non-string entries. Values identify
  effective IDs, including legacy fallback IDs. Compare using the existing NFC
  normalization and case-sensitive rules, and deduplicate repeated references. Treat
  strings as literal IDs, never paths or URLs to decode, resolve, or fetch. Recommend

- Only =depends_on= defines edges. Markdown links and =Blocked by= prose do not

  their source targets move; dependency IDs do not.

*** Dependency behavior and execution order
=A depends_on: [B]= means B must have =status: done= before A is ready. Keep persisted
status exactly =todo= or =done=; readiness is derived:

- *Ready:* a todo task with valid dependency metadata whose direct prerequisites all
  resolve uniquely to valid done tasks, or which has none.
- *Blocked:* a todo task with an unfinished or unresolved prerequisite, a dependency
  cycle, or invalid dependency metadata. Show the reasons.
- *Done:* the saved status. Do not change it based on dependency state, infer completion
  from descendants, or mark tasks complete in the UI.

Discover and validate all tasks, including completed tasks, before evaluating
dependencies. An absent, invalid, or conflicting target is an unresolved prerequisite,
not a satisfied one. Invalid =depends_on= must leave an otherwise valid task and its
body visible, marked with a dependency problem. Existing invalid status/title/ID
behavior still prevents an ordinary task row. Report dependency problems with source
paths and IDs even when completion is hidden.

Build the execution graph from unfinished tasks with edges from prerequisite to
dependent. Done prerequisites satisfy their incoming references and are removed from
this graph: their historical prerequisites do not reopen them or block their dependents.
Diagnose bad historical references on done tasks, but only cycles among unfinished tasks
prevent execution. Detect self-edges and multi-task cycles and name their members.

Use a stable topological sort; when multiple tasks are eligible, choose the smallest
effective ID by the existing case-sensitive code-unit comparison. Tasks with broken
dependency metadata, unresolved targets, or cycles, and all unfinished tasks
transitively dependent on them, have no valid execution rank. Show them after the
ordered work in a clearly labeled dependency-problems section, sorted by ID. Ordinary
blocked tasks whose prerequisites can be completed still get ranks after those
prerequisites. Unrelated work remains usable when part of the graph is broken.

Ranks describe an order in which the remaining tasks could be completed, not permission
to start every listed task immediately. For =A -> B -> C=, where the arrow means "must
finish before", show A, B, C, with only A ready. Reloading after A is marked done makes
B ready and removes A from the unfinished order.

- *Patch strategy.* The app host plans the edit from the file's bytes with the reader's
  own front matter parser: exactly one =status: todo|done= entry, block or flow style,
  plain or quoted, whose value alone changes, and the result must read back as the same
  body and front matter apart from =status=. Tags, anchors, explicit keys, duplicates
  and lookalikes in other values are refused with an explanation. Emacs applies the byte
  range only if the file still has the SHA-256 the plan was made from, so it needs no
  YAML at all.

- *Commands, freshness and refresh.* Buttons post JSON to =/tasks/action=; the app host
  resolves the ID and asks Emacs through the existing hosted action pipe (=task.status=,
  =task.edit=), one at a time, with an explicit target status. Emacs sends one bridge
  message, =refresh=, to a root's view after saving a file in it; the page replaces its
  =<main>= from a fetch of its own URL, keeping history, folds, scroll and focus, and
  also revalidates pages restored by Back/Forward and hidden pages once shown. No
  polling.

- Choose a format-preserving YAML patch strategy, including explicit behavior for valid
  structures that cannot be safely edited. Preserve the existing read format; do not
  quietly narrow discovery to accommodate the writer.

- Specify how command results, document freshness, and save notifications cross the
  existing bridge, and how refresh restores view context. Avoid adding a generic command
  framework or a background polling system for this scope.
