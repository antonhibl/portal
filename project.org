*** Problem and outcome
Portal terminals can live for an entire Emacs session, but their generic buffer names
make them difficult to recognize. The current terminal picker searches only names, and
ordinary terminals have no explicit project association or directory tracking after the
shell starts.

Make each terminal an informative Emacs buffer with a stable label, assigned project,
current directory, terminal title, and known process state. Expose this information
through a small Lisp interface and ordinary completion so existing buffer tools can use
it. The follow-up [[#terminal-consult-embark][Consult and Embark integration]] uses this
foundation for project-scoped selection and actions.

*** Scope and decisions
- Keep the buffer as the session's identity and lifetime owner. Keep user labels stable
  when applications change the terminal title; never recover identity by parsing a
  display name. Choose useful default names, disambiguating projects and worktrees that
  share a basename, and respect explicit user renames.
- Record the assigned project at creation separately from the shell's current directory.
  =cd /tmp= must not remove the session from its assigned project. Provide an explicit
  operation to reassign the project. Use canonical local roots, with a configurable
  resolver that defaults to =project.el= and can accommodate Projectile without
  requiring it.
- Cache metadata in Lisp. Bridge the native title and process-exited state, and adopt
  the pinned Ghostty wrapper's working-directory callback. Initialize the directory from
  the launch context until a reliable shell report arrives. Synchronize valid local
  directory reports with =default-directory= and =list-buffers-directory= for ordinary
  file and buffer commands. Do not treat a remote or container path as a host-local
  directory without enough context.
- Expose session enumeration, metadata, and filtering by assigned project to consumers.
  Keep ordinary and quick terminals distinguishable; preserve the quick terminal's
  existing naming, project identity, and display behavior.
- Enhance ordinary terminal completion with useful context through standard completion
  metadata. Matching must cover the chosen label, project, title, and directory rather
  than leaving all context in non-searchable annotations. Preserve the underlying buffer
  target independently of displayed text.
- Do not depend on Consult, Vertico, Marginalia, or Embark in core Portal. Ordinary
  buffer listings should display useful names and directories, while project-aware
  consumers can explicitly use assigned ownership instead of inferring it from the
  mutable directory.
- Report only facts that are available. An open shell is not proof that it is idle or
  busy, and a terminal title is not an authoritative process name. Rich
  command-completion, activity, and agent-status indicators can follow.

Before implementation, record the default naming format, behavior outside a project, and
policy for accepting directory reports. Keep these choices within the stable-label and
assigned-project contracts above.

*** Decisions
Recorded 2026-09-29, before implementation.

- *Label and naming.* A terminal's label is its buffer name: the name buffer lists,
  Consult and Ibuffer already show. Portal names an ordinary terminal once, when it
  starts, as =*LABEL: PROJECT*=: LABEL is =terminal= for a shell and the program's file
  name for =portal-terminal-start=, such as =*claude: portal*=; an explicit name is used
  as given. PROJECT is the root's last directory component, extended with parent
  components while another live terminal's root ends the same way, so worktrees named
  alike read =research/portal= and =portal=. Emacs adds =<2>= to repeat names. Portal
  never renames a terminal afterwards: titles, directory changes and project
  reassignment leave the name alone, so renames with =portal-terminal-rename= or
  =rename-buffer= stay. Lookups use buffer objects and roots, never names. Quick
  terminals keep =*portal-quick:ROOT*=.
- *Outside a project.* An ordinary terminal started outside a project has no assigned
  project, and PROJECT in its name is its abbreviated start directory. It appears only
  in all-terminal listings until reassigned. Quick terminals keep their start directory
  as their root there, as before.
- *Project resolution.* =portal-project-function= maps a local directory to a project
  root (default: =project.el= without prompting; =projectile-project-root= also fits).
  Portal stores its =file-truename= as a directory name, and quick terminals use the
  same function. A new terminal is assigned the project of its start directory, which is
  the current buffer's =default-directory=, so a terminal started from another terminal
  starts in that shell's reported directory. =portal-terminal-set-project= reassigns.
- *Directory reports.* Ghostty passes on OSC 7 reports only from this host, and its
  shell integration for zsh and bash sends one at each prompt. Portal accepts a report
  that is an absolute path, not remote syntax, and an existing directory, checked with
  file name handlers disabled so a report never starts TRAMP. It then sets the cached
  directory, =default-directory= and =list-buffers-directory=. Anything else is ignored
  and the last accepted directory, initially the start directory, stays.
- *Native changes.* The platform tells the core a terminal changed (title, directory or
  exit); the core sends one =terminal TARGET= record and sends no other for that view
  until Emacs inspects it, so a program retitling itself constantly cannot flood the
  pipe. Lisp reads the new facts with =portal--inspect=, which carries text of any
  length.

*** Acceptance criteria
- [X] Several terminals in one project have distinct, recognizable labels; identical

- [X] Title changes update metadata without overwriting a user label, including while

- [X] Supported shell directory reports update file-command context; missing or

- [X] Program exit is distinguishable from a live session and from a killed buffer.
  Closing a buffer removes its metadata without affecting other shells.
- [X] Standard completion searches the specified fields and resolves the chosen
  candidate to the correct buffer. Core behavior works with no optional completion or
  project packages installed.
- [X] Existing quick-terminal behavior and buffer-owned lifecycle remain intact.
- [X] Focused tests cover metadata updates, identity, project filtering, and fallback
  behavior; a graphical smoke test verifies real title/directory/exit events through the
  native bridge. Project checks pass.

*** Outcome

=portal-terminal-buffers=, =portal-terminal-metadata=, =portal-terminal-set-project= and
=portal-project-function= are the interface for
[[#terminal-consult-embark][Consult and Embark integration]]. =portal-terminal-choose=
searches name, project, directory and title.

Found while implementing:

- The native fact is =pwd=, not =directory=, which already names the start directory
  among a terminal's options.
- Ghostty with =wait-after-command= reported an exit only at the next key press, so

  and sets =abnormal-command-exit-runtime= to 0, so Ghostty reports every exit at once
  as a close request. Portal still keeps the view and its output, and the next key
  returns the keyboard to Emacs.
- Emacs's default completion styles match only from a candidate's start, so the
  =portal-terminal= category adds =basic= and =substring= to
  =completion-category-defaults=, as Emacs does for buffers. Users' styles still follow
  them, and overrides win.

*** Problem and outcome
Terminal sessions should be as easy to find and act on as project files and buffers.
Provide an optional Consult and Embark integration over Portal's ordinary terminal
buffers: project/all-session selection, searchable context, recent-use ordering,
previews, and contextual actions. Use existing Emacs completion and window navigation,
without adding a layout manager or dashboard.

*** Blocked by
[[#terminal-buffer-metadata][Terminal metadata and project ownership]] supplies stable
buffer identity, cached context, and project filtering. This integration must consume
that interface rather than introduce another metadata store or infer project ownership
from candidate names.

*** Scope and decisions
- Provide current-project and all-terminal commands. Allow widening a project selection
  to all projects. Resolve the project before opening the minibuffer; when invoked from
  a terminal, use its assigned project. Offer a documented Projectile adapter and retain
  a =project.el= default.
- Add optional terminal sources to =consult-buffer= and =consult-project-buffer=, with a
  configurable narrowing key. Avoid duplicate terminal entries in the ordinary mixed
  list. Retain the standard completion fallback when Consult is absent.
- Search compact candidates containing label, project, reported title, and current
  directory, preserving the underlying buffer identity. Display extra facts as
  annotations. Vertico and Orderless should work through the normal completion
  interfaces; they need no Portal-specific UI or hard dependency.
- Order the picker by recent intentional use. Freeze its ordering during a selection, do
  not count previews as visits, and handle buffers disappearing before confirmation.
  Keep cycle commands' ordering independent.
- Select into the current window by default. Support optional manual or debounced
  preview while preserving minibuffer keyboard ownership. Cancellation restores the
  previous buffer and native view placement. Portal has one native view per buffer, so
  preview must account for moving/resizing a live terminal, including one already
  displayed in another frame.
- Offer explicit new-terminal and named-terminal actions in the chosen project; a
  mistyped filter should not silently launch a shell. Exclude quick terminals by default
  and preserve their established display behavior if included.
- Supply Embark actions to select, rename, open Dired in the session directory, create
  another shell there, copy the directory, reassign the project, and end the terminal.
  Creating another shell does not clone a running process. Use the =buffer= candidate
  category to retain normal buffer actions and Ibuffer export; scope terminal-only
  actions to Portal targets.
- Keep termination consistent across picker actions and buffer-list tools. Ghostty's
  subprocess is not an Emacs =get-buffer-process=; do not rely on that API for state or
  termination confirmation. Keep switching/burying distinct from ending a session.
- Make the commands available through Portal's existing native input bridge. Document
  opt-in native bindings for the same buffer/project shortcuts users employ in Emacs,
  and resume the selected terminal only after completion ends. Handle selection from a
  quick-terminal panel deliberately.
- Isolate Consult-specific helpers in the optional adapter and document the supported
  package versions. The current project hook is =consult-project-function=, accepting
  =MAY-PROMPT=; do not copy obsolete config using =consult-project-root-function=.

Before implementation, record the command names, default preview policy, narrowing key,
and how the scoped Embark action map extends buffer actions. Study =consult-ghostel= as
a precedent, accounting for Portal's native views and focus ownership rather than
assuming its preview implementation transfers.

*** Decisions
Recorded 2026-09-29, before implementation, after reading =consult-ghostel= at the
pinned revision and Consult 3.10 and Embark 1.2 source.

- *Commands.* =portal-terminal-choose= (all terminals, still =C-b w=) and
  =portal-terminal-choose-project= (the current project's). In either, =M-a=
  (=portal-terminal-choose-map=) switches between the project's terminals and all of
  them, keeping the input. =portal-terminal-select= selects a terminal buffer read by
  name; Embark uses it as the default action. Both pickers resolve the project first: a
  terminal's assigned project, otherwise the frame's editing context
  (=portal-project-context=) through =portal-project-function=. Projectile users set
  that to =projectile-project-root= and =consult-project-function= to
  =(lambda (_may-prompt) (projectile-project-root))=.
- *Candidates and order.* One compact string per terminal (label, project, directory,
  title), carrying its buffer; exited and quick are annotations. Order is Emacs's buffer
  list, most recently selected first, with the current buffer last; it is read once when
  the picker opens and not re-sorted. An accepted selection is recorded by
  =switch-to-buffer=; previews use =norecord=. Cycling keeps creation order. A "New"
  group offers "New terminal in PROJECT" and "New named terminal in PROJECT...",
  starting at the project root (or the context directory outside a project). Completion
  requires a match, so no input ever creates a terminal.
- *Adapters.* =portal-terminal-consult.el= defines =portal-terminal-consult-mode=: the
  pickers read through =consult--multi=, and hidden sources
  =portal-terminal-consult-source= and =portal-terminal-consult-project-source= join
  =consult-buffer= and =consult-project-buffer= under narrowing key =t=, so the default
  mixed list shows each terminal once, as an ordinary buffer. The picker's "New" group
  narrows with =n=. =consult-customize= changes either key. Without the mode, the
  pickers use =completing-read= with category =portal-terminal=.
- *Preview.* Consult only, and manual by default: =M-.= through the sources'
  =:preview-key=;
  =(consult-customize portal-terminal-consult-source :preview-key '(:debounce 0.3 any))=
  makes it debounced. The preview window is the window the picker started from, or the
  editing window behind a quick panel. Quick terminals are not previewed. While the
  minibuffer is selected, a Portal view follows the window the minibuffer returns to, so
  a terminal shown in another frame or window moves into the preview and back when it
  ends. Placing a view never takes the keyboard, so typing stays in the minibuffer;
  =portal-input= resumes a terminal only after the command ends.
- *Embark.* Consult candidates keep category =buffer= (Consult's =multi-category=
  holding the buffer object); the fallback's =portal-terminal= candidates get a
  transformer to the same buffer. =portal-terminal-embark-mode= puts a target finder
  first in =embark-target-finders=: when the current target is a buffer naming a live
  Portal terminal, it becomes a =portal-terminal= target. Its map,
  =portal-terminal-embark-map=, has =embark-buffer-map= as its parent, so every buffer
  action remains, and adds: =RET= select, =r= rename, =d= Dired in its directory, =c=
  another shell there, =W= copy its directory, =p= reassign its project, =k= end it.
  Other buffers stay =buffer= targets with the unchanged map. Export uses Embark's
  collectors, so terminal candidates export to Ibuffer; a list mixed with the "New"
  group exports to Embark Collect, as mixed Consult lists do.
- *Ending terminals.* =portal-terminal-confirm-kill= (default t) asks before killing a
  terminal buffer whose program has not exited, through =kill-buffer-query-functions=,
  however it is killed: =C-x k=, Ibuffer, Embark, =C-b x=. Quick-terminal reset and
  forget keep their own prompt.
- *Quick terminals.* Excluded unless =portal-terminal-choose-quick= is non-nil; a chosen
  one opens in the quick panel. From a quick panel, the pickers select in the editing
  window behind it, leaving the panel open; cancelling returns to the panel.
- *Versions.* Tested with GNU ELPA Consult 3.10, Embark 1.2, Vertico 2.15 and Orderless
  1.8, which CMake downloads for the tests with pinned hashes, and with MELPA Consult
  20260829.1558 and Embark 20260610.302.

*** Acceptance criteria

- [X] Consult's ordinary and project buffer commands can narrow to terminals without

- [X] Recent-use order reflects accepted switches, stays stable while typing, and

Found while implementing:

- Embark's =RET= and the terminal map's actions are functions that Embark calls with the
  target's name, =portal-terminal-embark-select= among them, not commands that read it.
  Injecting the name into a prompt was fragile, and a command that read the current
  terminal could take the name as its answer.
- A view only follows the selected pane, so a Consult preview left a terminal shown
  elsewhere in place. While the minibuffer is selected, =portal-view= now treats the
  window it returns to as the selected pane (ADR 0001 and =CONTEXT.md= say so).

- Hiding a view ends its handoff, as the core's tests require, so a command that showed
  another terminal in the originating pane never resumed a terminal, though the prefix

  ended the handoff, or an error or explicit unfocus did. The user ending it sends an
  =escape= record, which each view remembers and Lisp reads from the pipe when finishing
  fails, even after a command that read no input (review of PR #46). =C-b n= and =C-b w=
  now resume the terminal they select.
- A terminal view closed but kept its buffer, and a quick terminal, are not previewed;
  Consult would otherwise show placeholder text.
- Consult 3.10 computes a hidden source's items only while it is narrowed to, and
  Vertico skips its update while input is pending. Stand-ins for =completing-read=
  cannot narrow, and the graphical tests must type as a person does. Batch Emacs opens a
  real minibuffer while it executes a keyboard macro, so the adapter suites type into
  one.
- With =portal-terminal-confirm-kill= off in the test suites, =C-b x='s old confirming
  =y= leaked into the next test; that test now answers the real question with the option
  on.

  nothing the platform calls can reach Emacs.

  =portal_timer_start(token, milliseconds)=, and two calls into the core:
  =portal_notify(type, target, fields, count)= and =portal_timer_fired(token)=. The
  header now says the platform calls the core only on the module thread, with borrowed
  arguments, and that no callback reaches Emacs.
- =portal--channel= keeps its behavior. =emacs.c= passes the descriptor from
  =open_channel= to =portal_channel_connect=, declared in the core's private
  =native/Core/channel.h=. On failure, the descriptor stays the caller's, the old pipe
  stays connected, and =emacs.c= closes it and signals with =strerror=.
- Decisions:
  - *Queue.* A singly linked list of records allocated with =malloc=, so sending one never moves the
    rest.
  - *Descriptors.* Connecting sets =O_NONBLOCK=, =FD_CLOEXEC= and =F_SETNOSIGPIPE=.
    Replacing or disconnecting closes the old descriptor once and never retries =close=.
    Reconnecting the same descriptor keeps it.
  - *Timers.* The platform's timers cannot be cancelled. The core cancels a retry by
    forgetting its token, which is never 0 or reused, so a stale callback neither writes
    nor starts another timer. Any connect cancels the pending retry, and at most one
    retry is pending.
  - *Write size.* A record, newline included, fits in =PIPE_BUF=, so each write is all
    or nothing. A short write, which POSIX rules out, would resume where it stopped. A
    new pipe always gets whole records.
  - *Errors.* =EINTR= retries at once, and =EAGAIN= retries after 20 ms. Any other
    error, such as =EPIPE=, leaves records waiting for Emacs to connect a pipe.
  - *Validation.* Words must be nonempty printable ASCII (0x21 to 0x7e), which is
    slightly stricter than before: the Swift check let control characters other than
    whitespace through. =notify= returns false only for a record it will never send
    (malformed, too long, or out of memory).
  - *Other platforms.* Other platforms are a future concern. Without =F_SETNOSIGPIPE=,
    =channel.c= stops with =#error=. Its comment records the Linux approach: block
    SIGPIPE in the writing thread and consume the signal a closed reader raises.
- Swift: =native/NativeEventChannel.swift= and =Views.channel= are gone.
  =native/CoreCalls.swift= holds =Core.notify=, which input, pane selection and the web
  bridge call, and the timer, =DispatchQueue.main.asyncAfter=.
  =native/Core/include/module.modulemap= names =portal.h= =PortalCore=, so SwiftPM and
  the standalone checks import it the same way. The checks link =channel.c= and use
  =channel.h= as their bridging header.
- The fake backend implements the timer: its timers fire only when a test fires them
  (=test/portal-fake-backend.h=). Its hosted app announces echoed messages with one
  =bridge= record, as the real bridge does. That replaces the "fake connected" line.
- README and =docs/terminal-input-bridge.md= describe the core's pipe, the new tests and
  the new check commands.

  =portal_toolbar_shortcut= about keys the app would get), with the same rules: text
  size with or without a toolbar and in passthrough; find only with a visible toolbar
  and the view owning the keyboard.
- =portal.h= no longer declares =portal_toolbar=, =portal_toolbar_theme=,
  =portal_toolbar_action=, =portal_input_owner= (now core-internal, in =input.h=) or
  =portal_web_edit= (now a click on the EDIT button). It adds the primitives
  =portal_toolbar_draw=, =portal_toolbar_focus=, =portal_web_zoom=, =portal_web_find=
  and =portal_web_call=, reusing =portal_web_go= and =portal_terminal_set_font_size=,
  and the calls =portal_toolbar_clicked=, =portal_toolbar_typed=, =portal_web_loaded=,
  =portal_web_history=, =portal_web_found=, =portal_web_returned= and
  =portal_web_headings=. It now holds only 25 primitives and the calls into the core;
  the README lists them.
- =emacs.c= reads the theme's JSON with Emacs's =json-parse-string=, as it reads
  terminal bindings, into a =portal_colors= of plain sRGB values; a malformed color
  leaves the platform's default, as before.
- Swift keeps drawing: =Toolbar.swift= builds the strip from a =ToolbarState= copied
  from the snapshot, with the same layout, SF Symbols, tooltips, accessibility, tracking
  areas and appearance handling, and turns colors into =NSColor= objects. =ToolbarModel=,
  =NativeToolbar=, the JSON refresh fingerprint, =WebToolbar='s zoom, TOC and find
  logic, the terminal's text-size policy and =NativeInput.ownership= are gone.
  =WebToolbar.swift= is WebKit glue for the contents script, script calls and find.
  Every view now sits in a =NativeContainer=, which shows a strip only when the core
  draws one, and =NativeView= keeps the last snapshot to show wherever the view moves.
- Decisions:
  - *Snapshot, not revision.* The core builds a =portal_toolbar= after anything that may
    change a toolbar and draws it only when it differs from the last one drawn (a
    refused draw is retried next time). No module counts changes, and the platform
    compares nothing.
  - *Async results.* The core owns them. Each find and script call carries a token that
    is never reused; one search runs at a time, as a count by the contents script then a
    native find; newer text replaces waiting searches; =portal_web_loaded= starts a new
    generation that drops an older search's result and searches again. Results for
    another token, or a closed view, reach nothing. The heading count comes from the
    contents script's reports and the TOC call each load makes; a commit resets it to
    none.
  - *Focus.* Opening find calls =portal_toolbar_focus=, which gives the field, part of
    the view, the keyboard and reports it. Closing find calls =portal_view_focus= only
    while the input core says the view has the keyboard. The dot calls
    =portal_view_focus=, or =portal_input_escape= like Command-Escape.
  - *Script calls.* One primitive, =portal_web_call=, runs a function of a shared script
    with a JSON argument that crosses as data, and returns an integer; it serves both
    the TOC and the find count.
  - *Parity scope.* Closing a closed find field now does nothing, where it ran an empty
    search and could refocus the page. Headings reset at commit rather than at a
    provisional navigation's start. An absent =:toolbar= means none rather than an
    error; Lisp always passes one.
